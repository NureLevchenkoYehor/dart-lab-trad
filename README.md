# Trad

## Лабораторна робота №1. Функції та обробка колекцій

### Структура програми

Програма складається з точки входу `bin/trad.dart` і чотирьох бібліотек у каталозі `lib/`.

| Бібліотека             | Призначення                                                                |
| ---------------------- | -------------------------------------------------------------------------- |
| `lib/csv_parsing.dart` | Низькорівневий розбір рядка CSV на список текстових полів                  |
| `lib/core.dart`        | Оголошення типу `Track`, конвертація полів на `Track`, форматування звіту  |
| `lib/validation.dart`  | Перевірка коректності значень `Track` за бізнес-правилами                  |
| `lib/processing.dart`  | Операції над колекціями: фільтрація, агрегація, сортування тощо            |

## Обґрунтування архітектури

1. Відокремлення CSV-парсеру від моделі даних (`lib/csv_parsing.dart` та `lib/core.dart`): Функція `parseCsvRow` нічого не знає
   про сутність `Track` і працює виключно на рівні синтаксису CSV (враховуючи екранування подвійних лапок, коми всередині лапок
   тощо). Якщо джерело даних зміниться або знадобиться замінити базовий парсер на сторонній чи додати підтримку інших форматів
   (TSV, JSON), змінюється лише цей окремий модуль розбору, не зачіпаючи сутність треку та формування звітів.
2. Відокремлення валідації від розбору (`lib/validation.dart`): Розбір рядка перевіряє виключно синтаксичний формат (чи має
   рядок 5 колонок, чи можливо розібрати дату та ціле число тривалості), повертаючи `null` за наявності структурних помилок.
   Валідація ж перевіряє змістовні бізнес-правила предметної області (чи назви не порожні, чи не перевищує тривалість 24 години,
   чи рік релізу перебуває в межах від 1860 року до поточного року). Такий поділ дозволяє незалежно модифікувати бізнес-правила
   без втручання в механіку парсингу.

### Обґрунтування вибору типів даних

- `Track` (`typedef Track = ({...})`) — анонімний іменований запис (record): Для цілей першої лабораторної роботи сутність є
  зручним незмінним контейнером даних без складної власної поведінки. Використання такого типу У наступній роботі дозволить
  перейти на повноцінний клас без зайвих труднощів.
- `artists: List<String>` — список рядків для авторів/виконавців треку: Список зберігає впорядкованість авторів згідно з
  вхідними даними (перший автор зазвичай є основним лід-виконавцем, подальші — запрошеними гостями чи співавторами). Колекція
  `Set<String>` використовується лише як тип поверненого значення у функції `extractUniqueArtists`, де потрібна дедуплікація
  імен.
- `releaseDate: DateTime` — дата релізу треку: На відміну від збереження дати простим рядком, тип `DateTime` забезпечує
  коректне хронологічне порівняння, зручний доступ до компонентів дати (`year`, `month`, `day`) та календарну арифметику
  різниці дат (обчислення віку треку в днях у фільтрі `releasedWithin`).
- `duration: Duration` — тривалість звучання треку: Замість збереження простого цілого числа мілісекунд `int`, тип `Duration`
  інкапсулює одиниці часу, унеможливлюючи помилки плутанини секунд і мілісекунд. Він також надає готові обчислювані геттери
  (`inMinutes`, `inSeconds`), спрощуючи форматування виводу та розрахунок сумарної і середньої тривалості.
- `Track?` як результат роботи `tryParseTrackCsvRow`: Повернення `null` у разі невідповідності кількості стовпчиків або
  неможливості конвертації дати чи тривалості дозволяє конвеєру безпечно пропустити некоректний рядок і продовжити обробку
  інших записів.
- `List<String>` як результат валідації (`validateTrack`): Функція повертає список повідомлень про всі виявлені порушення
  (порожній список свідчить про повну валідність треку). Альтернатива (викидання винятку на першому ж порушенні) не дозволила б
  побачити повну картину помилок запису за один прохід.
- `Map<String, List<Track>>` та `Map<String, Duration>`: Асоціативні масиви з назвою альбому як ключем забезпечують швидке
  групування треків за альбомами (`groupTracksByAlbum`) та подальше обчислення статистичних агрегатів (середньої та сумарної
  тривалості кожного альбому) за константний час доступу $O(1)$.
- `bool Function(Track)` (функціональний тип-предикат): Використовується як фабрика предикатів у функції вищого порядку
  `releasedWithin({required int days, DateTime? beforeDate})`. Це дає змогу гнучко конфігурувати умови фільтрації для
  стандартного методу `Iterable.where()`, замикаючи цільову дату й часовий інтервал.

### Обґрунтування щодо оператора `!`, ключового слова `late` та типу `dynamic`

Відповідно до наскрізних вимог до коду та правил захисту робіт:

1. Оператор `!` (null assertion operator / force unwrap):
   - Використання в коді: Не використовується жодного разу.
   - Обґрунтування: Усі потенційно nullable значення обробляються засобами Sound Null Safety:
     - явні перевірки на `null` (`if (track == null)`, `if (releaseDate == null || durationMs == null)`);
     - типізоване відсіювання відсутніх значень через `whereType<Track>()`;
     - оператори надання значень за замовчуванням `??` (наприклад, `targetDate = beforeDate ?? DateTime.now()`).  
     Це гарантує захист від раптових помилок під час виконання (`TypeError` або `NullThrownError`).
2. Ключове слово `late` (відкладена ініціалізація):
   - Використання в коді: Не використовується жодного разу.
   - Обґрунтування: Усі змінні, константи та структури даних ініціалізуються безпосередньо в місці оголошення або через
     параметри функцій. Відмова від `late` унеможливлює виникнення винятку `LateInitializationError` у runtime і забезпечує
     незмінність (`final`/`const`) та передбачуваність стану програми.
3. Тип `dynamic` (динамічна типізація):
   - Використання в коді: Не використовується жодного разу.
   - Обґрунтування: Усі типи даних строго задекларовані або однозначно виводяться статичним аналізатором Dart. Це гарантує
     перевірку типів на етапі компіляції (`dart analyze`) і повністю виключає помилки `NoSuchMethodError` під час виконання.
     Для забезпечення цього у файлі `analysis_options.yaml` увімкнено лінтер-правила
     `no_dynamic_casts` та `no_raw_types`.

### Обґрунтування сторонніх залежностей із `pub.dev`

- `path` (`dependencies`). Слугує для кросплатформної роботи зі шляхами до файлів.
  Обрано як офіційний пакет Dart, що коректно нівелює відмінності роздільників між ОС.
- `lints` (`dev_dependencies`). Підключає набір правил `package:lints/recommended.yaml` для статичного аналізу коду.
  Обрано як офіційний стандарт стилю та аналізу для консольних Dart-проєктів.
- `test` (`dev_dependencies`). Забезпечує написання й запуск модульних тестів за допомогою команди `dart test`.
  Обрано як офіційний стандарт тестування в екосистемі Dart із повною підтримкою інструментарію.
